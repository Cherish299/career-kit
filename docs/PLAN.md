> 从个人职业画像出发，打通岗位发现、匹配分析、材料生成、辅助投递、进度跟踪与笔面试准备。
>
> - 项目代号：CareerOS
> - 建议仓库名：career-kit
> - 计划版本：v1.0 ｜ 制定日期：2026-08-18 ｜ 实施负责人：老张
> - 总体周期：12 周；第 4 周交付可演示 MVP

**执行原则**：先闭环、后扩展；先辅助投递、后自动化；先验证 3—5 个目标官网，再建设通用采集框架。第 4 周必须出现一个可从头演示的完整流程。所有里程碑均以"可运行、可测试、可演示"为验收标准。

## 执行摘要

**核心目标**：4 周内完成"个人画像 → 岗位录入与解析 → 匹配分析 → 定制简历 → 投递记录"的 MVP 闭环；12 周内形成包含岗位采集、个人主页、面试准备与辅助填表的可公开演示版本。

### 成功标准
- **业务闭环**：用户能在 10 分钟内完成从导入个人资料到创建一条岗位投递记录
- **工程质量**：核心规则、数据迁移、岗位解析和状态流转均有自动化测试，主分支持续通过 CI
- **演示价值**：公开 Demo 不需要真实个人信息或 API Key 即可体验核心流程
- **个人价值**：系统能够服务 2026 年秋招，支持 AI 开发、大模型应用、RAG/Agent 等目标岗位
- **开源质量**：仓库不包含 node_modules、个人绝对路径、密钥和乱码构建产物，并提供清晰许可证与文档

### 范围基线
| 类别 | 本期定义 |
| --- | --- |
| 目标用户 | 以本人为第一用户，同时兼顾应届生和 AI 技术岗位求职者 |
| MVP | 个人画像、手动岗位录入/解析、规则匹配、简历版本、投递看板 |
| 12 周版本 | 增加官网采集、公开个人主页、JD 定向面试准备、辅助填表 |
| 暂不承诺 | 无人值守批量投递、覆盖所有招聘平台、通用社交网络、商业化多租户 |

## 产品定位与设计原则

**一句话定位**：以个人职业画像为唯一事实源，提供岗位发现、材料生成、投递执行和求职复盘的一体化个人求职操作系统。

**五条设计原则**
1. **单一事实源**：教育、项目、技能等事实只在个人画像维护一次，简历、主页和投递表单均引用它
2. **岗位驱动**：每份简历版本、求职信、准备清单和投递记录都必须关联具体岗位
3. **人机协同**：系统负责解析、匹配、生成和辅助填写；用户负责事实确认与最终提交
4. **可解释**：匹配分数必须展示硬条件、关键词、语义证据和缺口，不能只给黑盒总分
5. **隐私分层**：公开主页、分享链接和私有工作台使用不同字段白名单，默认最小公开

**核心场景**
- 导入现有 Resume Kit 数据，形成结构化个人职业画像
- 粘贴招聘官网链接或 JD 文本，系统抽取岗位字段并提示缺失项
- 对照个人画像输出匹配优势、硬性缺口和简历修改建议
- 为该岗位生成独立简历版本并记录生成来源、时间和修改历史
- 打开官网完成投递，同时自动创建投递记录和后续任务
- 基于 JD 和个人项目生成复习清单、面试题与项目追问

## 模块规划

模块以共享数据模型连接，不允许各自维护重复的姓名、经历、技能或岗位副本。

| 模块 | 主要能力 | 核心实体 | 优先级 |
| --- | --- | --- | --- |
| 个人中心 Profile Hub | 教育、科研、项目、技能、作品、目标岗位、城市与行业偏好；支持现有 JSON 导入 | Profile、Experience、Skill、Preference | P0 |
| 岗位雷达 Job Radar | 岗位录入、官网采集、搜索筛选、收藏、去重、变更检测、匹配分析 | Company、Job、JobSource、JobSnapshot | P0/P1 |
| 材料工作室 Asset Studio | 岗位定制简历、求职信、Markdown/PDF 导出、个人主页与数字名片 | ResumeVersion、Portfolio、ApplicationAsset | P0/P1 |
| 投递管线 Application Pipeline | 待投递队列、状态看板、事件时间线、提醒、数据统计、辅助填表 | Application、ApplicationEvent、Task | P0/P2 |
| 面试准备 Interview Kit | 接入现有题库，按 JD 生成专题清单、模拟题与复盘记录 | Question、PracticeRecord、InterviewPlan | P1 |

### 模块验收边界
- **个人中心**：同一份资料可被简历、主页、匹配和辅助填表复用；支持字段级公开权限
- **岗位雷达**：至少支持手动 JD 与 URL 两种入口；解析失败时允许人工修订；岗位有来源与快照
- **材料工作室**：每个岗位可绑定一个或多个简历版本；生成内容不得擅自新增事实和数字
- **投递管线**：状态变更追加事件而非覆盖历史；最终提交前必须由用户确认
- **面试准备**：题目与具体 JD 要求、个人项目或岗位方向存在可追溯关联

## MVP 范围与验收

MVP 截止第 4 周周末。演示必须从空数据库或样例账号开始，不依赖开发机特殊路径，不使用真实手机号、邮箱和 API Key。

| 编号 | 能力 | 交付说明 | 验收标准 |
| --- | --- | --- | --- |
| P0-01 | 个人画像 | 导入现有 Resume Kit JSON 并可继续编辑 | 导入后教育、项目、技能字段正确；校验错误可读 |
| P0-02 | 岗位录入 | 粘贴 JD 文本或岗位 URL，保存结构化岗位 | 关键字段可编辑；保存来源 URL 与原始文本 |
| P0-03 | 匹配分析 | 硬条件+关键词规则输出匹配报告 | 展示优势、缺口、证据；同输入结果可复现 |
| P0-04 | 简历版本 | 基于岗位复制并生成定向简历 | 不覆盖母版；记录目标岗位和版本时间 |
| P0-05 | 投递看板 | 创建投递、切换状态、查看事件时间线 | 状态流转合法；每次变更留下事件 |
| P0-06 | 基础工程 | 统一启动、构建、测试、CI 和示例数据 | 新环境按 README 可运行；主分支 CI 通过 |

**本期不做**：不做无人值守批量投递，不绕过验证码、登录验证或平台限制；不承诺覆盖所有招聘网站；不在 MVP 引入微服务、Kubernetes 或多租户权限；不让 LLM 成为唯一匹配器（硬条件和规则结果必须可以独立运行）；不公开真实投递数据、个人手机号、出生日期和模型 API Key。

## 技术架构

采用**模块化单体**作为首版架构：统一 Web 前端、FastAPI 后端、PostgreSQL 数据库和可选后台任务进程。采集任务数量和并发确实增长时再拆分独立 Worker。

| 层次 | 技术选择 | 选择理由 |
| --- | --- | --- |
| Web 前端 | React/Next.js；保留现有原生 JS 规则引擎，通过适配层逐步迁移 | 避免一次性重写，优先形成统一壳层和路由 |
| 后端 API | Python + FastAPI + Pydantic | 与 AI、抓取、数据处理技术栈一致，Schema 表达清晰 |
| 数据库 | PostgreSQL；开发期可使用 Docker Compose | 支撑关系数据、全文检索、版本与事件记录 |
| 后台任务 | MVP 使用定时任务；后期按需引入 Redis/Celery | 避免首版过度工程化 |
| 官网采集 | HTTP 解析优先，必要时 Playwright；每个来源实现适配器 | 优先结构化接口、JSON-LD 与站点公开数据 |
| 匹配引擎 | 硬过滤 + 关键词/BM25 + 语义匹配 + LLM 解释 | 分层计算、可解释、可单测 |
| 部署 | 前端静态/边缘托管；后端容器；托管 PostgreSQL | 开发与生产配置分离，密钥仅在服务端 |

### 核心数据流
1. 个人画像写入统一 Profile Schema，生成稳定 ID 和字段可见性配置
2. 岗位入口保存原始内容，再通过解析器生成标准 Job 字段；任何人工修订单独记录
3. 匹配引擎读取 Profile 与 Job，输出 MatchReport 及逐项证据
4. 材料工作室以 Profile 事实、Job 要求和模板生成 ResumeVersion，不修改母版
5. 用户确认投递后创建 Application；后续状态更新追加 ApplicationEvent
6. Interview Kit 根据 Job、MatchReport 和已提交 ResumeVersion 生成准备计划

### 代码仓库建议结构
```
apps/web：统一前端、公开个人主页和工作台界面
services/api：FastAPI 接口、认证、业务编排和数据库访问
services/crawler：招聘官网来源适配器与定时采集任务
packages/profile-schema：个人画像与导入迁移规则
packages/resume-engine：现有模板、体检、导出和版本生成能力
packages/job-matcher：硬过滤、关键词匹配、语义匹配与解释
packages/interview-kit：现有题库、判分与 JD 定向准备能力
extensions/application-assistant：后期浏览器辅助填表，不进入 MVP
```

### 核心数据模型
| 实体 | 用途 | 关键字段 |
| --- | --- | --- |
| profiles | 用户职业画像主记录 | id、display_name、summary、visibility、updated_at |
| experiences | 教育/科研/实习/项目/校园经历 | profile_id、type、title、organization、content、start/end |
| skills | 技能和证据 | profile_id、name、level、evidence_experience_id |
| preferences | 求职偏好与硬约束 | roles、locations、industries、job_types、graduate_year |
| companies | 公司统一实体 | name、aliases、career_site、industry |
| jobs | 标准岗位 | company_id、title、location、requirements、source_url、status |
| job_snapshots | 岗位历史快照 | job_id、content_hash、raw_content、captured_at |
| match_reports | 匹配结果 | profile_id、job_id、scores、strengths、gaps、evidence |
| resume_versions | 岗位定制简历 | profile_id、job_id、parent_id、content、created_at |
| applications | 一次投递的当前状态 | profile_id、job_id、resume_version_id、status |
| application_events | 不可丢失的投递历史 | application_id、event_type、from/to_status、occurred_at |
| interview_plans | 岗位准备计划 | application_id、topics、questions、progress |

### 关键状态机
Application 状态：发现 → 收藏 → 待投递 → 已投递 → 笔试 → 一面 → 后续面试 → Offer / 拒绝 / 放弃。状态变更必须经过后端校验，并追加事件记录。

**数据约束**：岗位原始内容、标准化字段、人工修订和 AI 生成结果必须分开保存。任何生成式内容都应记录模型、提示词版本和输入摘要，便于复现与回滚。

## 匹配算法实施方案

匹配结果分层组合，MVP 先做确定性规则，第 6 周以后再引入语义召回和重排。任何阶段都必须输出证据和缺口。

| 层次 | 输入 | 实现与约束 | 时间 |
| --- | --- | --- | --- |
| 硬条件层 | 毕业年份、学历、城市、岗位类型、必须证书 | 不满足时标记阻塞，不由语义分掩盖 | 第 3 周 |
| 关键词层 | 技能、工具、领域术语、职责动作 | TF/IDF 或加权词典；输出命中证据 | 第 3 周 |
| 语义层 | 经历与岗位职责的语义相似度 | Embedding 召回；保存模型版本 | 第 6 周后 |
| 重排层 | 对 Top 候选做更精细相关性判断 | Cross-encoder 或 LLM 打分，控制成本 | P2 |
| 解释层 | 优势、缺口、简历修改建议 | 只解释已计算证据，禁止编造事实 | 第 3—4 周 |

## 官网采集实施规范

- 优先使用公开 API、JSON 接口、RSS、JSON-LD 和 Sitemap，再考虑页面解析
- 每个来源实现独立 Adapter：discover、fetch、parse、normalize、health_check
- 以 source + external_id 为主键；没有 external_id 时使用公司、标题、地点和内容摘要去重
- 保存内容哈希和抓取时间，只在内容变化时写入新快照
- 设置合理频率、超时、重试和并发上限；记录 robots 和网站条款核验结果
- 解析器使用固定 HTML 样例回归测试，网页结构变化时能迅速发现
- 公开仓库只保留合法的适配器代码和匿名样例，不提交登录 Cookie 和抓取数据全集

## 辅助投递实施规范

自动化默认停在"填好并等待确认"。只有正式 API 或明确允许的渠道才能进入自动提交；验证码、登录校验和最终声明不得绕过。

| 级别 | 能力 | 说明 | 计划 |
| --- | --- | --- | --- |
| L1 | 跳转与建档 | 打开官网岗位页，同时创建待投递记录 | MVP |
| L2 | 字段映射 | 根据 Profile 把姓名、教育、项目映射为候选值 | 第 9 周 |
| L3 | 辅助填写 | 扩展填写常见文本框、下拉框和日期字段 | 第 9 周 |
| L4 | 材料上传 | 选择并上传绑定该岗位的 ResumeVersion | P2 |
| L5 | 确认提交 | 用户检查、确认声明并手动触发提交 | 长期默认 |

## 隐私与安全

| 主题 | 设计要求 | 验收检查 |
| --- | --- | --- |
| 个人信息 | 公开/分享/私有三级字段可见性；默认私有 | 手机号、生日、投递记录不得进入公开 Demo |
| API Key | 仅服务端环境变量或短期会话；不得写入 Git 和构建产物 | 上线前运行密钥扫描 |
| AI 输入 | 只发送完成任务所需字段；界面明确提示发送内容 | 隐藏板块不进入模型输入 |
| 岗位来源 | 保存来源 URL、抓取时间和解析日志 | 尊重公开访问规则和来源许可 |
| 自动投递 | 用户最终确认；记录自动填写字段和行为日志 | 禁止绕过验证码或平台限制 |
| 备份导出 | 导出时说明是否包含个人数据；提供清除本地数据功能 | 样例与真实数据严格分离 |

| 高 | 范围失控 | 同时重写前端、做爬虫和自动投递导致 MVP 延期 | 冻结第 4 周 MVP；P1/P2 不得抢占 P0 |
| 高 | 招聘网页变化 | 解析器快速失效 | Adapter 隔离、HTML fixture、健康检查和失败告警 |
| 高 | 个人数据泄露 | 公开 Demo 或日志带入真实信息 | 匿名样例、字段白名单、密钥扫描、发布检查 |
| 中 | AI 输出编造 | 简历出现不存在的事实或数字 | 母版事实约束、差异预览、人工确认、生成审计 |
| 中 | 自动投递受限 | 验证码、动态表单、账号风控 | 采用辅助填表；站点级适配；最终人工提交 |
| 中 | 技术栈过重 | 维护基础设施多于做产品 | 模块化单体；Redis/Celery 按真实需求引入 |
| 中 | 题库准确性 | 公开内容被面试官发现错误 | 逐题来源、verifiedAt、技术审校和勘误机制 |

## 项目管理与 GitHub 发布

- main 始终保持可运行；功能通过 feature 分支和 Pull Request 合并
- 提交信息使用 feat、fix、refactor、test、docs、chore 等前缀
- 每个 PR 只解决一类问题，附测试结果、界面截图和数据迁移说明
- M1、M2、M3 分别创建 GitHub Release 和演示记录

### Issue 标签
- area:profile / area:jobs / area:assets / area:pipeline / area:interview
- priority:P0/P1/P2
- type:bug / type:feature / type:test / type:docs

### 公开仓库发布清单
- README 顶部有一句话定位、截图、在线 Demo 和快速启动
- 根目录存在 LICENSE、.gitignore、统一 package/任务命令和贡献说明
- CI 在干净 Linux 环境完成构建、单元测试、冒烟测试和密钥扫描
- Release 提供可下载单文件或部署链接，不提交 node_modules
- 题库和外部资料列出来源、许可证边界和准确性声明
- 仓库 Topics、描述和项目演示视频与秋招简历表述一致

### 度量与复盘
| 维度 | 指标 | 目标 |
| --- | --- | --- |
| 产品效率 | 从岗位录入到创建投递记录的中位耗时 | MVP ≤ 10 分钟 |
| 解析质量 | 样例岗位关键字段准确率 | M1 ≥ 90%（人工核对） |
| 匹配可用性 | 匹配报告中有证据支持的建议比例 | 100% |
| 工程稳定性 | 主分支 CI 通过率 | ≥ 95% |
| 采集稳定性 | 目标官网适配器 7 日成功率 | M2 ≥ 95% |
| 求职效果 | 投递→笔试/面试/Offer 转化率 | 只做个人趋势，不设虚假 KPI |

每周复盘问题：本周是否产生可运行、可展示的增量？哪个功能真正减少了求职操作时间？是否新增了重复数据源或难以维护的技术组件？测试是否覆盖了本周新增的关键失败场景？下周唯一最重要的交付是什么？
